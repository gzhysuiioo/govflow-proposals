# DAO 治理提案与执行平台

## 用途

提案生命周期、投票与计票规则、委托与声誉、资金库支出与多签执行、时间锁与回滚、治理审计。

本仓库是可持续演进的自托管 Go 应用。领域核心位于 `govflow/`，命令入口位于 `cmd/govflow/`。

```bash
go run ./cmd/govflow demo
go run ./cmd/govflow version
go test ./...
```

## 本地资金库

到期提案可以对本地资金库执行真实转账。状态持久化在单个 JSON 状态文件中，
余额、提案登记与执行凭据一起保存；退出后重新打开可继续查询与执行。
全部行为只依赖 Go 标准库，离线可复现。

### 命令

```bash
# 初始化资金库（只有新文件可以初始化，已有文件不会重置余额）
govflow init --state ./treasury.json --balance 10000

# 登记已通过提案：编号非空，保留时间锁与动作原文
# 同编号相同内容的重试幂等返回；内容不同报冲突
govflow register --state ./treasury.json \
  --id gip-7 --timelock 5000 \
  --action transfer:audits:25000 \
  --action transfer:legal:1000

# 按编号执行（当前时间由调用方通过 --now 提供）
# 只有 passed、时间已达时间锁、动作非空的提案可首次执行；成功后变为 executed
govflow execute --state ./treasury.json --id gip-7 --now 5001

# 查询余额（未出现过的收款账户为 0）
govflow balances --state ./treasury.json
govflow balances --state ./treasury.json --account audits

# 查询提案状态（register 与投票两种来源都可查询）
govflow proposal  --state ./treasury.json --id gip-7
govflow proposals --state ./treasury.json

# 创建投票提案：成员名单与权重、可选委托、法定人数、投票窗口、时间锁与有序动作
govflow create-vote --state ./treasury.json --id gip-8 \
  --member alice:300 --member bob:200 --member carol:100 --member dave:400 \
  --delegate bob:alice --delegate carol:alice \
  --quorum 600 --start 100 --deadline 200 --timelock 300 \
  --action transfer:audits:100

# 按提案编号投票（时间由调用方通过 --now 提供）
# 只有最终代表本人可投票；bob、carol 已委托给 alice，由 alice 代表其权重
govflow vote  --state ./treasury.json --id gip-8 --voter alice  --choice for     --now 150
govflow vote  --state ./treasury.json --id gip-8 --voter dave   --choice against --now 150

# 截止时刻或之后计票；再次计票返回首次结论
govflow tally --state ./treasury.json --id gip-8 --now 200

# 通过后的提案直接交给 execute 执行，无须再 register；被拒绝的提案不能执行
govflow execute --state ./treasury.json --id gip-8 --now 300

# 查询执行凭据（按成功提交先后顺序）
govflow receipt  --state ./treasury.json --id gip-7
govflow receipts --state ./treasury.json

# 所有资金库命令支持 --json
govflow execute --state ./treasury.json --id gip-7 --now 5001 --json
```

命令失败时原因输出到 stderr，域错误退出码为 1，参数错误为 2。

### 动作与数值规则

- 动作只支持 `transfer:<账户>:<金额>`；收款账户不能为空或包含冒号。
- 金额只接受十进制数字表示的正整数，且与全部余额一起限定在有符号 64 位整数范围内。
- 执行按动作原顺序从资金库扣款并增加对应账户余额，同一账户可以连续收款。
- 整项提案先完整预演再一次性提交：编号不存在、时间未到、状态不符、动作格式错误、
  余额不足或金额计算溢出都返回明确原因，不产生部分转账，失败不消耗执行机会。

### 投票提案

- 编号与成员编号必须非空，成员不得重复；权重为正整数；权重、法定人数与全部时间
  均限定在有符号 64 位整数范围内，成员总权重不得溢出；法定人数在 1 至总权重之间；
  时间满足 `0 <= 开始 < 截止 <= 时间锁`。任一非法条件整项拒绝，不落盘部分内容。
- 成员与委托的输入次序不影响相等性比较，动作仍按原文及顺序比较。同编号、全部内容
  相同的创建重试返回已有提案且不改变状态；内容不同报冲突。创建后规则与内容不可修改。
- 每人最多委托一名名单内成员，委托可继续转交；自委托、重复指定与循环一律拒绝。
  最终未再委托的人代表沿途全部成员投票，未委托者代表自己。查询展示每名成员的
  委托路径、最终代表与原始权重。
- 成员编号非空即可，允许包含冒号，冒号可以出现在编号开头、末尾或连续出现
  （如 `:alice`、`team:bob`、`a:`），编号逐字保留并区分大小写；`--member`
  仍按最后一个冒号切出权重，故权重部分必须仍是十进制正整数。
- `--delegate FROM:TO` 原文不按固定位置切分：结合本次完整成员名单枚举原文中
  每个冒号位置，候选切分两端都必须非空。恰好一对成员同时命中时按该对创建；
  两对或更多同时命中时报委托有歧义（参数错误，退出码 2，错误列出原文与全部
  成员对），即使其中某种解释随后会触发自委托、重复或循环，也不拿业务规则替
  用户选定另一种解释。原文没有冒号或不存在两端均非空的写法属格式错误
  （退出码 2）；存在非空写法但没有任何一对都在名单属域错误（退出码 1）。
  唯一确定成员对之后，自委托、重复指定与循环仍一律拒绝；成员与委托参数的
  排列先后不影响同一项委托的含义。
- 只有最终代表可以投赞成或反对：每位代表一张票，票重等于归到其名下的全部原始权重。
  首次投票只接受 `开始 <= now < 截止`；不在名单或已委托出去的人投票报明确错误。
  同一代表相同选择的重试始终返回首次记录；改投另一选择报冲突，不静默覆盖。
- 首次计票必须在截止时刻或之后，否则报“时间未到”且状态不变；未投权重不计入参与量。
  赞成与反对权重之和达到法定人数且赞成严格多于反对才通过；平票或参与不足均拒绝。
  计票只确定状态，不转账；再次计票返回首次结论；计票后拒绝新票，即使传入窗口内时间。
- 通过后的提案直接由 `execute` 执行，无须再登记；被拒绝的提案不能执行，
  已执行提案不退回通过。`register` 与投票提案共用编号：任何一方都不能覆盖另一方
  或绕过投票结论。
- 查询（文本与 `--json`）展示逐票代表、票重、选择、首次投票时间，以及汇总权重与
  首次计票时间。创建、投票、计票在多线程/多进程并发及重开后保持一致：成功重试不
  追加记录。保存失败不能一概说成“失败不留部分变化”：失败发生在状态文件替换之前时
  确实不留任何部分变化；替换已成功、仅随后目录同步失败时，票据其实已经写入，只是
  持久性未确认。两种结果的区分与处置见“故障与损坏处理”。

### 幂等性与并发

- 一项提案只允许成功一次。再次执行即使传入不同时间，也返回首次成功凭据，
  不重新检查资格或扣款；重试不追加凭据。
- 凭据包含提案编号、首次执行时间、成功提交序号 order、每项动作原文及其在提案中的
  顺序编号 index、资金库与收款账户变动前后的余额；这些顺序信息只来自明确保存的值。
- 多线程或多进程同时操作同一状态文件时：同一提案只产生一份成功记录；
  不同提案依据实际已提交余额判断能否支出，查询不会看到部分转账。
  串行化由进程内互斥锁与 `flock` 文件锁共同保证。

### 故障与损坏处理

- 执行保存失败按发生位置分两种结果。失败在状态文件替换之前（临时文件写入、
  fsync 或原子改名失败）：保留上次完整状态，返回具体错误，不产出凭据，
  提案保持 passed，条件满足后仍可执行。状态文件已替换成功、仅随后的目录
  同步失败：转账、executed 状态与执行凭据其实已经写入——这既不能解释为
  完全没有执行，也不表示这次变更的持久性已得到确认。此时 `execute` 仍以
  退出码 1 结束，但标准输出照常给出已写入的完整凭据（普通文本与 `--json`
  的凭据对象与成功时相同），标准错误说明“执行记录已写入，但持久性未确认”
  并带上提案编号与具体失败原因；Go 调用方同时取得完整凭据与可由
  `errors.Is(err, govflow.ErrDurabilityUnconfirmed)` 识别的错误
  （`*govflow.DurabilityError`，`Cause` 为具体失败原因）。该告警不撤销
  已写入的转账、不把提案退回 passed、不删除凭据；随后正常查询即可看到
  整项提案已执行、余额与全部动作留痕对应，再次执行（即使传入不同时间）
  仍返回首次凭据，不再次扣款。收到告警后应通过 `receipt`/`balances` 等
  查询确认实际状态，而不是假设未执行，也不是假设持久性已确认。
  登记来源与投票通过来源的提案适用同一规则。
- 投票保存失败同样按发生位置分两种结果，判断“这张票有没有记录”只看失败位置，
  不能只凭退出码 1 就认定没投上。用户在投票窗口内以有资格的最终代表提交首次投票、
  看到 `vote` 以退出码 1 结束时，按下列两种情况处理；命令入口、投票窗口
  （`开始 <= now < 截止`）与重试规则都不变。
  - 失败在状态文件替换之前（临时文件无法创建、写入失败、fsync 失败或原子改名失败）：
    此次没有新增票据。原有票据、委托关系、窗口时间与提案状态保持失败前的原样，
    错误保留具体保存原因（如 permission denied），这不是投票业务拒绝，也不占用
    该代表的首次投票机会。恢复正常保存条件后，只要仍在窗口内，重新提交即按首次
    有效投票记录，票据时间采用新的提交时间。若恢复时已经到达截止时刻，这张尚未
    记录的首次票仍会被拒绝——先前的失败尝试不算投过，不能借此越过截止边界。
  - 状态文件已替换成功、仅随后的目录同步失败：这是“票据已写入，但持久性未确认”，
    既不能说成完全没有投票，也不能保证这次变更已可靠保存。与执行告警不同，
    `vote` 在普通文本和 `--json` 下都只把原因写到标准错误（退出码 1），标准输出
    没有票据；Go 调用方 `CastVote` 得到 nil 票据与可由
    `errors.Is(err, govflow.ErrDurabilityUnconfirmed)` 识别的错误
    （`*govflow.DurabilityError`，具体原因保留在 `Cause` 中）。因此不要照搬
    `execute` 告警“stdout 已带凭据、直接采信”的处理方式：此时应先经
    `proposal` 等查询确认实际状态。随后的正常查询可以看到已写入的完整票据
    （代表、归集权重、选择、首次投票时间）。重复提交相同选择始终返回这张首次
    记录——即使传入的时间已经到达截止时刻，返回的仍是首次代表、归集权重、选择与
    首次投票时间，不追加票据；改投另一选择仍报冲突，原票不会被覆盖。
  - 带委托权重的对照示例（成员 alice:300、bob:200、carol:100、dave:400，
    bob 与 carol 委托给 alice，法定人数 600，窗口 [100,200)）：dave 已在 120
    投出 400 权重反对。alice 在 150 投赞成（其票重含 bob、carol 委托，共 600）
    时若保存失败发生在替换之前，则没有任何赞成票据，恢复后在 160 重投成功，
    到期计票为赞成 600、反对 400、参与 1000，达到法定人数且赞成严格多于反对，
    结论通过；若恢复后直到 200 才提交，这张首次票按截止边界被拒绝，到期只有
    dave 的票，赞成 0、反对 400、参与 400，未达法定人数，结论拒绝。同一次 150
    提交若失败发生在改名之后（目录同步失败），则 alice 的 600 权重赞成票已经
    写入，到期计票与第一种恢复情形相同：赞成 600、反对 400、参与 1000、通过。
    即已写入的票按归集权重正常计入参与量，未写入的票不参与；委托成员不另计。
    投票与计票全程不转账、不生成执行凭据，资金余额不变；通过后只有在时间锁之后
    另行 `execute` 才会发生提案动作的转账。
- 执行中进程退出，重开只能看到执行前或执行后的完整状态。
- 已保存成功但尚未返回就退出，重试仍取得原凭据。
- 状态文件损坏（截断、非法 JSON、未知字段、重复键、余额与凭据重放不一致、
  投票票据的票重/代表与名单及委托明细不一致、计票结论与票据重放不一致等）
  一律拒绝打开，不会重建或覆盖原文件；对损坏文件执行 init 同样被拒绝。
  每张已保存票据必须明确写出 representative、weight、support、voted_at 四个字段：
  任一缺失、为 null 或 JSON 类型不符（support 只接受布尔值，weight/voted_at
  只接受 int64 整数）都判整份文件损坏，错误原因标明提案编号、票据下标与字段
  及缺失/空值/类型不符；查询与计票不给部分结果，也不把缺损补成反对票或时间 0。
  明确写出的 false 是有效反对票，窗口从 0 开始时明确写出的 0 是有效投票时间。
  每项已保存的投票提案还必须明确写出 ballots 字段，且它必须是 JSON 数组：
  字段缺失、为 null，或写成对象、字符串、数字、布尔值，都判整份状态文件
  损坏，错误标明提案编号、ballots 字段及缺失/空值/类型不符；尚在投票、已经
  通过、被拒绝和已经执行的提案适用同一条要求，不能因为计票汇总恰好为零，或
  资金余额仍能与执行凭据对应，就把缺损列表补成空数组。缺损记录上查询不返回
  空票据或其它提案的部分结果、投票不追加新票（已投代表不能借缺损列表再次
  投票）、计票不产生零参与权重的新结论、执行不继续转账；同一文件中的另一项
  完整提案也一并拒绝使用，原文件保持原样，普通文本与 --json 都只把原因写到
  标准错误并以退出码 1 结束。明确写出的空数组仍表示确实无人投票：正常创建
  提案后可直接查询并在窗口内接受首次投票，无人投票到期计票仍得到赞成、反对
  与参与权重均为零的拒绝结论，该记录之后仍可正常查询；空数组合法只说明列表
  没有缺损，不放宽状态与计票一致性要求，完整票据仍保留原顺序、代表、权重、
  选择和首次时间。
  每项已保存的投票提案还必须明确写出 start_at，且它必须是有符号 64 位
  范围内的 JSON 整数：字段缺失、为 null，或写成字符串、布尔值、对象、数组、
  小数、指数形式、越界数字，都判整份状态文件损坏，错误标明提案编号、start_at
  字段及缺失/空值/类型不符。start_at 决定投票窗口何时开启：原本在 100 开始、
  200 截止的提案缺了 start_at，若被读成 0 就会把窗口向前扩大，代表在 50
  投出的首次票也可能被接受；因此开始时间只能来自明确写出的值，不能从票据
  时间、截止时间、时间锁或其它记录推算，也不能补零后继续使用，即使票据、
  计票结论与执行凭据都能与其余内容核对一致也不宽免。尚在投票、已经通过、
  被拒绝和已经执行的提案适用同一条要求；缺损记录上查询不返回其它完整提案或
  余额的部分结果、投票不追加票据、计票不产生新结论、执行不转账，整份文件中
  只要有一项投票提案不合要求就一并拒绝，原文件保持原样，普通文本与 --json
  都只把原因写到标准错误并以退出码 1 结束，Go 调用方按既有的状态损坏错误
  （ErrStateCorrupt）识别这类拒绝。明确写出的开始时间 0 仍合法：正常创建
  开始为 0、截止为 1、时间锁为 1 的提案后查询保留 0，有资格的最终代表在
  0 首次投票被接受、在 1 首次投票仍被拒绝；正数开始时间原值保留，开始之前
  不接受首次投票，相同选择的投票重试规则保持不变。类型合法的取值仍须符合
  既有的 `0 <= 开始 < 截止 <= 时间锁` 规则。
  每份执行凭据的 order 与每项动作的 index 同样必须明确写出，值为非负 JSON
  整数（int64 范围内，不接受 null/字符串/布尔/小数/指数/超界），并分别等于
  该凭据在成功执行记录中的位置、该动作在所属凭据中的位置（均从 0 起）。
  第一份凭据缺 order、任一凭据第一项动作缺 index 都判整份文件损坏：不会因为
  记录恰好排在第一项就补出 0，也不按数组位置重新编号，余额与动作原文能够重放
  一致同样不宽免；错误标明提案编号、字段、缺失/空值/类型不符/位置不符的具体
  原因（index 还标明所属动作位置）。明确写出的 0 是有效序号，第一项位置正常
  读取；同一收款账户连续出现多项动作时仍按原顺序分别保留，不合并、不重排。
  旧版本写出的、不含投票提案字段的状态文件继续可读；旧提案不补造投票记录，
  但旧版本兼容不宽免已有执行凭据的 order/index 缺失，也不宽免已保存投票
  提案自身的 ballots 与 start_at 缺失：不含整张投票提案表可以，表内提案
  省略票据列表或开始时间不行。
  每份执行凭据的 actions 必须明确写出、为 JSON 数组且至少包含一项动作留痕：
  字段缺失、为 null、写成其它 JSON 类型或读出后没有任何动作都判整份文件
  损坏——成功执行必须实际包含动作，无动作提案在执行时只会得到“没有动作”
  的拒绝而保持 passed，不可能产生成功凭据；因此不能只因凭据与提案的动作
  数量相等（都为零）、order/executed_at 合法且余额重放一致就接受。错误
  标明凭据位置与提案编号；登记来源与投票通过来源适用同一要求，即使投票
  明细与通过结论完全合法也不宽免。尚未执行的无动作提案仍可登记、创建
  投票、正常查询与计票，通过后执行继续按“没有动作”拒绝，状态、余额与
  凭据记录保持原样；真正含转账动作的凭据（含转账后资金库余额恰好为零）
  照常读取。
- 状态文件中的每个 JSON 字符串（对象键与字段值同等适用，含提案编号、成员编号、
  收款账户与动作原文）都必须可精确表示：字符串含有非法 UTF-8 字节序列，或
  `\u` Unicode 转义中的高代理项（U+D800–U+DBFF）与低代理项（U+DC00–U+DFFF）
  没有按“高后立即低”的正确次序成对出现时，整份文件判为损坏。encoding/json
  默认会把这两类内容悄悄改写成替换字符 U+FFFD 且不报错——账户名被改写后余额
  与凭据仍可能重放一致，查询却会展示另一个名字；因此读取在解码前逐字节扫描，
  被改写的文本不可能参与编号匹配、重复键判断或凭据重放。错误说明是字节编码
  非法还是代理项未配对，并给出从文件开头按零计数的字节位置；未配对转义的位置
  指向该转义开始的反斜杠。坏字符串即使出现在本次没有查询的另一项提案中，也拒绝
  读取整份文件，原文件内容保持原样。合法字符不被误拒绝：中文、表情等合法
  UTF-8 文本与一对合法高低代理项转义照常读取，同一字符直接写出或采用合法转义
  不影响编号匹配与重复键判断；用户明确写出的 U+FFFD（直接字节或 `\uFFFD`
  转义）是合法字符，不能仅凭读取结果含有它认定损坏；反斜杠自身被转义后出现的
  “`\uD800`”字样（源码拼写 `\\uD800`）按普通文本保留，不参与代理项配对。
  字符合法同样不宽免其它任何损坏原因。
- 提交采用临时文件、fsync、原子改名加目录 fsync；不同状态文件的资金与执行记录互不影响。
